## 1. 背景与目标

### 1.1 业务背景
企业内部经常出现需要多个部门协同研究、形成共识或经过裁决才能落地的"重大事项"，常见场景包括：

- 跨部门战略决策（路线图优先级、组织调整）
- 流程优化（响应延迟、合规缺口）
- 政策制定与征询（HR 政策、办公制度）
- 预算与资源争议（超支审批、资源分配）

这些事项往往涉及多个利益相关方，存在分歧时需要会商甚至裁决；无显著争议时仍需要按程序征求意见。当前缺少统一平台承载，导致：

1. **流程不透明**：审批节点散落在邮件/IM/Excel 中，进度不可见
2. **责任不可追溯**：谁在哪个环节做了什么决定，事后难以复盘
3. **重复决策**：缺少沉淀，相似问题反复争论
4. **超期失控**：没有自动督办，关键事项一拖再拖

### 1.2 产品目标
- **闭环管理**：覆盖从提报到评价的完整生命周期
- **过程可视**：任何人都能看到任意问题当前在哪个节点、卡在哪里
- **审计可查**：每一次状态变更、每一条留言、每一个文件都有时间戳和操作人
- **争议可控**：分歧期触发会商裁决路径，结论形成约束力

### 1.3 非目标 (Out of Scope)
- 不做权限/角色（首版任何人可对任何事项操作；后续可挂 RBAC）
- 不做项目管理（甘特图、依赖关系等不在范围）
- 不做工单系统（客户服务工单走客服系统）
- 不做长文档协作（落实方案的细致编辑走 Confluence）

## 2. 用户与场景

### 2.1 用户身份模型
**不区分角色**——任何登录用户都可执行任何阶段动作。但每一次动作都会记录 `actor_user_id`，确保审计追踪。

| 身份概念 | 说明 | 系统中体现 |
|---|---|---|
| 提报方 | 发现并提报问题的人 | `problem.submitter_id` |
| 承办方 | 牵头办理的单位/人 | `problem.handler_dept` / `handler_name` |
| 协办方 | 共同参与的单位/人 | `problem.participants[]` |
| 裁决方 | 出现争议时做最终决定的部门 | 由协同流程动态指定 |
| 评价方 | 对结果打分的相关方 | `evaluation.party` |

> 同一个用户可在同一个问题里同时扮演多种身份。

### 2.2 典型场景
1. **战略决策**（争议路径）：研发-产品就 H2 路线图分歧 → 提报 → 战略部审核分办 → 委员会研提两套折中方案（标记争议） → 会商 2 轮 → COO 裁决 → 落实 → 评价
2. **流程优化**（共识路径）：客服响应延迟 → 提报 → 运营审核 → 运营优化办研提 3 项举措（无争议） → 全员征求意见 → 落实 → 评价
3. **超期督办**：海外合规事项 → 法务提报后等海外事业部 → 超期 3 天 → 系统通知 + 看板高亮 + 留言 @ 催办

## 3. 业务流程

### 3.1 核心流程图

```
①问题提报 ──► ②审核分办 ──► ③研提举措 ──┬─[存在争议]──► ④会商研究 ──► ⑤争议裁决 ─┐
                                          │                                         │
                                          └─[无显著争议]────► ⑥征求意见 ────────────┴──► ⑦督导落实 ──► ⑧评价反馈
```

### 3.2 节点说明

| # | 节点 | 关键动作 | 推进条件 |
|---|---|---|---|
| 1 | 问题提报 | 描述、设置优先级、上传材料 | 创建即完成 |
| 2 | 审核分办 | 通过/退回/不予受理；指派承办单位 | 决策提交 |
| 3 | 研提举措 | **关键分支点**：列出举措、标记每条是否有争议；按争议总数决定下一站 | 提交并选定分支 |
| 4 | 会商研究 *(争议路径)* | 多轮会商，记录共识与遗留分歧 | 标记会商结束 |
| 5 | 争议裁决 *(争议路径)* | 主管方对每个争议点出结论 | 发布裁决 |
| 6 | 征求意见 *(共识路径)* | 公开征集反馈，按建议修订 | 标记结束 |
| 7 | 督导落实 | 跟踪每条举措的进度，记录阶段性进展 | 申请办结 |
| 8 | 评价反馈 | 4 个维度打分 + 文字评价 + 是否归档最佳实践 | 提交即闭环 |

### 3.3 分支规则
- **判定时机**：仅在 `propose` 阶段提交时判定，由用户在表单中显式打开"存在争议"开关。
- **判定结果**：
  - `dispute`：进入 `meeting → arbitrate → implement`
  - `consensus`：进入 `consult → implement`
- **不可回退**：分支选定后保存到 `problem.branch`，后续阶段都按该分支走。如需修改，需重置到 `propose` 重新选定（管理员操作）。

### 3.4 状态映射

| 当前阶段 | `problem.status` |
|---|---|
| review | pending |
| propose, implement, evaluate | processing |
| meeting | meeting |
| arbitrate | arbitrate |
| consult | consulting |
| evaluate（且 evaluation 已提交） | done |
| 任意阶段 + 超期 | overdue（覆盖状态） |

## 5. 非功能需求

### 5.1 性能
- 看板首屏 < 1.5s（10k 问题量级）
- 问题列表分页加载 < 800ms（50 条/页）
- 办理弹层打开 < 600ms
- 状态机推进接口 < 300ms

### 5.2 兼容性
- 浏览器：Chrome / Edge / Safari 最新两个大版本，不兼容 IE
- 屏幕：1366×768 起，最佳 1920×1080+
- 数据库：PostgreSQL 12+ / **KingbaseV8 PG 兼容模式**

### 5.3 可观测性
- 后端：Spring Boot Actuator + stdout 日志（INFO+），关键业务在 service 层 DEBUG
- 前端：浏览器控制台错误捕获（后续接 Sentry）

### 5.4 安全
- v1：仅 X-User-Id 标识（demo），无鉴权——内网部署
- v2 计划：接入 OAuth2 / 公司 SSO / RBAC
- 文件：MinIO bucket 不开公网，全部经后端中转

### 5.5 可维护性
- 状态机使用枚举 + 引擎类，新增节点修改一处即可
- 前后端均有单元测试（19 + 13）
- 测试覆盖核心业务路径（完整争议流程、完整共识流程）

## 6. 数据指标

### 6.1 业务指标
- **问题办结率**：周/月 done 数 ÷ 提报数
- **平均办结时长**：done 问题的（评价日 - 提报日）均值
- **争议触发率**：dispute branch 数 ÷ 完成 propose 数
- **平均会商次数**：dispute 路径 problem 的会商历史条数均值
- **超期占比**：overdue 数 ÷ 在办数
- **单位满意度**：按承办单位聚合 evaluation.overall 均值

### 6.2 系统指标
- 接口 P50/P95 响应时长
- 每日新增 problem / message / attachment 数
- MinIO 存储增长曲线
